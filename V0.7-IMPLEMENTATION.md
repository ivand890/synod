# Synod v0.7 Implementation Backlog

Prepared: 2026-08-10

Baseline: `v0.6.3` (`738c9d1`)

Roadmap scope: SYN-070 through SYN-074

## Readiness decision

The TypeScript 7 foundation required by v0.7 is released and the local baseline
passes all 135 tests. Product implementation can start without another
foundation release and without a new production dependency.

One prerequisite must be implemented before a truthful checkpoint delta or a
recovery bundle is possible: the current canonical checkpoint stores only the
branch, `HEAD`, changed-path count, and aggregate fingerprint. It does not store
the normalized per-path identities that produced that fingerprint. An accepted
dirty checkpoint therefore cannot currently explain a path that later becomes
clean, distinguish which lane changed, or supply recovery material.

v0.7 will add that missing snapshot as a backward-compatible canonical record,
then build delta, export, restore, and handoff behavior on the same normalized
representation.

## Contracts fixed before implementation

### Safety boundary

- Delta, bundle verification, and handoff generation are read-only.
- Export's only durable effect is the explicitly selected bundle destination.
  It may acquire and clean up Synod's standard orchestration lock and use a
  temporary sibling while writing, but it must not mutate the worktree, Git
  index, commits, refs, remotes, or canonical Synod records.
- Restore is the only new v0.7 recovery command allowed to mutate project files
  or the Git index. It requires an explicit destination checkout, completes all
  validation before the first mutation, and restores the pre-operation
  worktree and index after any failure.
- No v0.7 command stages, commits, pushes, deploys, accesses the network, or
  follows a symlink outside the project or bundle root.
- Existing `.synod/` exclusions and the special user-owned portions of
  `AGENTS.md` and `.codex/config.toml` remain identical to v0.6.3.

### Checkpoint snapshot

Add `.synod/checkpoint.json` as a mutable, uninstall-preserved record. Its
schema-1 payload contains:

- the checkpoint branch, base `HEAD`, and worktree fingerprint;
- a deterministic, path-sorted list of relevant dirty entries;
- separate `HEAD`, index, and worktree identities where they differ;
- raw-byte SHA-256 identities, Git modes, absence markers, and symlink targets;
- rename source/destination metadata and an orthogonal binary marker;
- a content hash, calculated over the snapshot payload without the hash field,
  that is also referenced by the canonical checkpoint.

The state/event schema remains version 1 because the checkpoint snapshot
reference is an optional, additive field that old v0.6.3 validators already
tolerate. New checkpoints always include it. An existing checkpoint can be
upgraded safely when its recorded branch, `HEAD`, and legacy fingerprint all
match a fresh live capture. A historical checkpoint that no longer matches the
live checkout remains readable, but delta/export must fail closed with a stable
recovery instruction until the user explicitly records a new checkpoint. Synod
must never synthesize historical snapshot material from a different live
worktree.

The snapshot is written in the same orchestration transaction as
`state.json`, `events.jsonl`, and `STATUS.md`. Hash mismatch, missing material,
or an unsafe path makes the canonical read fail closed.

### Delta model

The shared delta engine compares two normalized snapshots and returns path
records with independent properties rather than a lossy single status string:

- path and optional rename source;
- staged change: added, modified, deleted, renamed, copied, type-changed, or
  unmerged;
- unstaged change using the same vocabulary;
- untracked state;
- binary state;
- before/after mode and content identities.

Path display uses repository-relative POSIX separators on every platform and
never embeds file contents. Text output groups staged, unstaged, and untracked
paths and labels renames, deletions, and binary entries. JSON returns the same
records without parsing the text view.

The engine includes changes between checkpoint `HEAD` and live `HEAD`, then
applies the recorded index/worktree overlays on both sides. If the checkpoint
commit or required Git objects are unavailable, it fails closed instead of
reporting the current `git status` as historical truth.

### Recovery bundle format

Use a deterministic directory bundle so Node's standard library is sufficient
and the package gains no runtime dependency:

```text
<destination>/
  manifest.json
  objects/
    <sha256-hex>
```

`manifest.json` schema 1 records:

- bundle ID, format version, Synod version, and the acknowledged snapshot's
  deterministic capture timestamp;
- source branch/`HEAD`, checkpoint fingerprint, snapshot hash, and last
  canonical event sequence/hash;
- every tracked index/worktree entry needed to reconstruct the checkpoint;
- opt-in untracked entries;
- mode, type, size, and SHA-256 for every object;
- deterministic rename metadata for diagnostics.

Objects contain raw bytes, including binary files and symlink targets. Content
addressing deduplicates staged/worktree copies. The manifest is serialized with
stable key and path ordering. Export writes a temporary sibling, fsyncs and
closes its files, verifies the completed bundle, atomically reserves a
destination that did not previously exist, then publishes `manifest.json` last
as the atomic completion marker.

Export first requires the live branch, `HEAD`, index, and worktree fingerprint
to match the acknowledged checkpoint exactly; snapshot hashes alone cannot
recreate unstaged or untracked bytes that have since been replaced. Ignored
paths are never bundled. If the checkpoint contains untracked files, an export
without the explicit untracked opt-in fails rather than producing an incomplete
recovery artifact. Dirty submodules are unsupported in the first format and
fail closed with a stable error until their nested repository contract is
specified.

### Verification and restore

Verification performs all of these checks without writing:

1. Resolve the bundle and checkout roots without following unsafe ancestors.
2. Parse all external JSON as `unknown` and validate exact schema values.
3. Reject absolute paths, traversal, backslash aliases, empty components,
   duplicate normalized paths, case-fold collisions where relevant, and parent
   /child file conflicts.
4. Reject missing, extra, oversized, or hash/size-mismatched objects.
5. Require the exact base `HEAD` and an otherwise clean destination checkout.
6. Precompute the expected restored checkpoint and require its fingerprint to
   equal the manifest fingerprint.

Restore snapshots the destination index and affected filesystem entries into a
private transaction journal before mutation. It reconstructs the index and
worktree from raw objects, recaptures the checkpoint, and commits only on an
exact fingerprint match. On any error it restores both filesystem entries and
the exact original index bytes; rollback failure uses a distinct stable error
and preserves the journal for manual recovery.

### Canonical handoff

Handoff is a generated projection, not a new source of truth. It reads the
validated state/event chain, the live checkpoint/delta, and an optional verified
bundle reference supplied by the caller. Text and JSON include:

- canonical checkpoint and live drift;
- active/reviewing task and exact revision;
- latest acceptance and verification evidence for that revision;
- blockers, incomplete dependencies, and unresolved acceptance/verification
  gates;
- legal next transitions derived from the transition table;
- verified bundle ID/path/hash, or an explicit `not supplied` state.

It does not inspect `GOAL.md`, `PLAN.md`, `STATE.md`, `WORKLOG.md`, or chat
history for authoritative values and does not write `STATUS.md` or another
handoff file implicitly.

  transactional checkpoint writes, integrity checks, upgrade planning, and

  interruption fail closed or recover atomically.
- No existing text, JSON, exit-code, deep-import, or package-smoke assertion
  changes except documented additive fields/files.

## Delivery sequence

Use four reviewable pull requests, all against the protected `main` branch:

1. SYN-070A/B: snapshot plus read-only delta.
2. SYN-071A/B: bundle format, verifier, and export.
3. SYN-072A: transactional restore and adversarial rollback.
4. SYN-073A/074A: handoff, installed cross-platform recovery smoke, docs, and
   the `v0.7.0` release preparation.

Each pull request must keep the full suite and package smoke green. The final
release still follows the repository's reviewed squash-merge, signed tag,
protected npm environment, npm/GitHub parity, provenance, and installed CLI
verification path.

## Definition of v0.7 ready to release

- Every accepted dirty checkpoint has a validated snapshot or an explicit
  historical-material-unavailable state.
- Delta text and JSON explain all required path/lane categories without writes.
- Exported bundles are deterministic, self-verifying, local-only, and complete.
- Fresh exact-base checkouts restore the recorded index/worktree fingerprint.
- Corruption, unsafe paths, wrong bases, conflicts, and injected interruptions
  fail closed with tested stable errors and exact rollback.
- Canonical handoff output needs neither user-owned state notes nor chat history.
- The installed artifact passes the recovery drill on every supported CI
  runtime surface and contains compiled JavaScript, not TypeScript source.
