# Synod v0.9 Implementation Backlog

Prepared: 2026-08-11

Baseline: `v0.8.0` (`e63b4e90f70ac6d4ede325b3a0dbcef51dbb88ba`)

Roadmap scope: SYN-090 through SYN-094

## Readiness decision

The recoverability and durable-ownership prerequisites are released. The exact
baseline supplies canonical events and checkpoints, recursive Codex session
discovery, cumulative-token reset/reroute handling, role-bearing subagent
metadata, observable wait metrics, generated handoff context, and explicit
task leases. v0.9 can therefore begin without another foundation release.

The existing `usage` command is a whole-session aggregate by model. It is not
yet sufficient for v0.9 because it does not clip observations to a canonical
interval, retain thread/role attribution, classify coordination activity, or
bind a budget decision to the exact observation that caused it.

Implementation begins with three supporting contracts:

1. Parse each rollout once into a normalized, timestamped activity timeline.
   Compute cumulative-counter deltas before applying interval boundaries so a
   report cannot count pre-interval activity or double count a reset.
2. Resolve event, checkpoint, and task selectors from the validated canonical
   state/event chain, then use one half-open interval convention across token,
   coordination, budget, cost, and rotation reports.
3. Add a one-way orchestration schema-3 migration for optional task budgets and
   explicit phase rotations. Reporting remains read-only; only dedicated
   commands may record an observation or supervisor decision.

No new production dependency is required. Exact CLI spelling may change during
implementation, but the state, safety, attribution, and acceptance contracts
below are fixed.

## Baseline audit

- `src/usage.ts` already discovers active and archived descendants, parses
  cumulative token counters, handles counter resets, follows model reroutes,
  and aggregates input, cached input, output, reasoning, and total tokens.
  It currently discards record timestamps, per-thread rows, agent roles, turn
  activity, current-context observations, and the source rollout identity.
- `src/app-server.ts` exposes the thread path, parent identity, source kind, and
  session tree needed to locate rollouts. Subagent rollout `session_meta`
  records additionally expose parent thread, agent path, nickname, and role.
  Root sessions require the explicit normalized role `supervisor`.
- `src/wait.ts` already reports wait mode, wake count, fallback polls, and
  elapsed duration for one invocation. Historical supervisor coordination is
  visible separately in rollout function calls such as `spawn_agent`,
  `followup_task`, `send_message`, `wait_agent`, `list_agents`, and
  `interrupt_agent`.
- Real pilot rollouts contain timestamped `token_count`, `task_started`,
  `task_complete`, `context_compacted`, function/custom-tool calls and their
  outputs, plus subagent role metadata. Older/newer Codex versions may omit or
  rename a signal, so completeness must be explicit per metric.
- `src/orchestration.ts` uses schema 2. Canonical events have stable sequence,
  ID, timestamp, task/revision fields, checkpoint identity, and a hash-linked
  full-state snapshot. Optional budgets and rotations cannot be added as
  unvalidated ad-hoc payloads; they require schema 3 and a preserved schema-2
  prefix.
- `src/handoff.ts` already derives live tasks, unresolved gates, correction
  policy, leases, proposals, recovery choices, checkpoint drift, and legal next
  transitions from canonical records. Rotation advice can be additive if its
  policy and measurement interval are explicit.
- `synod usage` and `synod handoff` are read-only. v0.9 keeps that property and
  does not make reporting dependent on a writable project.

## Contracts fixed before implementation

### Measurement and safety boundary

- Rollout files and the Codex App Server are local observed evidence, not
  Synod-owned telemetry. v0.9 reads them locally and never uploads usage,
  prices, project state, prompts, messages, or tool payloads.
- Usage, coordination, cost, status, and ordinary handoff reports are
  read-only. They do not acquire a writer lease, advance a task, acknowledge a
  checkpoint, record a budget decision, rotate a phase, change Git, or contact
  a pricing service.
- Raw message bodies, tool arguments, tool outputs, reasoning text, and prompt
  content are never copied into a report or canonical event. Only normalized
  identities, timestamps, counts, durations, completeness flags, token
  counters, and configured prices are retained.
- A missing rollout, malformed required counter, unreadable descendant, cycle,
  duplicate thread identity, timestamp regression, or ambiguous canonical
  selector fails closed for exact reports. Optional unsupported metrics are
  labelled unavailable; they are never silently reported as zero.
- Active session trees are always labelled incomplete. Closed intervals remain
  reproducible only while every selected rollout identity and required record
  remains readable and unchanged.
- Token counts are usage evidence, not invoices. Monetary output is absent
  unless the caller supplies an explicit dated price file.

### Canonical interval semantics

Every report resolves one normalized interval:

- `start`: a canonical event sequence/ID/hash and timestamp, an acknowledged
  checkpoint fingerprint/snapshot hash and capture time, or the first canonical
  event for a task;
- `end`: an explicit canonical event, the terminal `DONE`/`SUPERSEDED` event for
  a completed task, or a local capture boundary for live `since` reports;
- inclusion: `(start, end]` for timestamped rollout observations;
- provenance: selected root session, descendant set, rollout file identities,
  canonical state/event identity used to resolve the boundaries, and capture
  time;
- completeness: closed or active interval, missing/unsupported signals, and
  whether every discovered descendant was readable through the end boundary.

Token deltas are calculated across the complete rollout stream before interval
filtering. A token observation at the start boundary belongs to the preceding
interval; one at the end boundary belongs to the selected interval. This
prevents filtering from treating the first in-range cumulative counter as new
usage. A counter decrease starts a new counter epoch and contributes its
current non-negative values exactly once. A model reroute changes attribution
for later observations only.

A live local capture records each selected rollout's byte length, streamed
SHA-256 prefix hash, last included record timestamp, and discovered descendant
set. Later activity is outside that closed measurement prefix. A descendant
created after the end boundary is excluded; a descendant without enough
creation/path evidence to establish that ordering makes the closed report
ambiguous. The deterministic measurement payload uses the interval end as its
capture time; an optional volatile generation time is outside the report
identity.

The selectors behave as follows:

- event: resolve by sequence or ID, verify the event hash through the complete
  canonical log, and optionally close at a second exact event;
- checkpoint: bind to the acknowledged checkpoint fingerprint, snapshot hash,
  capture time, and the canonical event that introduced that identity;
- task: begin at that task's first canonical event and close at its first
  terminal event, or at capture time when still live. A task report includes
  all activity in the selected session tree during the interval and separately
  identifies lease-bound owner threads; it does not pretend unrelated
  supervisor work can always be assigned to one task.

If two canonical boundaries share a timestamp, event sequence breaks the
canonical tie but rollout observations at that timestamp cannot be split
between them. Such an interval is rejected as temporally ambiguous unless the
boundaries also carry an explicit future rollout cursor. v0.9 does not invent
sub-timestamp ordering.

### Normalized usage and role attribution

The rollout parser emits timestamped facts rather than a pre-aggregated map:

- thread/session identity, parent, source, rollout path identity, and role;
- active model and model-context-window observation;
- input, cached input, output, reasoning output, and total-token delta;
- counter epoch/reset marker;
- turn start/completion/abort and duration where supplied;
- context compaction;
- normalized tool-call start/output pair and duration where both timestamps
  exist.

Role resolution is deterministic:

- a root selected session is `supervisor`;
- a subagent uses `session_meta.source.subagent.thread_spawn.agent_role` when
  present;
- an unrecognized child source is `unknown`, never inferred from its model or
  task name.

Reports aggregate by thread, model, and role without losing their cross-product
identity. Totals retain the current contract that cached input is included in
input and reasoning output is included in output. Additional exclusive values
(`uncachedInput = input - cachedInput`) are derived only after validating that
the inclusive counters are consistent.

### Coordination overhead classification

Coordination is classified from normalized function calls, not from natural
language:

- spawn: `spawn_agent`;
- follow-up/message: `followup_task` and `send_message`, reported separately
  and with a combined total;
- wait: `wait_agent`, with requested and observed duration when available;
- supervision: `list_agents` and `interrupt_agent`;
- implementation tool calls: non-coordination function/custom-tool calls;
- compaction: explicit `context_compacted` facts, de-duplicated against the
  paired `compacted` record when both describe one compaction;
- failed tool calls: outputs that carry a structured error or a recognized
  local failure status.

Retry count is emitted only when Codex supplies an explicit retry relationship
or when a failed call and its retry share a stable retry/call identity. Similar
adjacent commands are not assumed to be retries. If that identity is absent,
`retries.available` is false rather than reporting a fabricated zero.

Call durations pair by `call_id`. Missing output leaves the call incomplete;
duplicate starts/outputs, negative durations, or cross-thread pairs are
rejected. Tool names are reported, but arguments and outputs are not.

### Orchestration state schema 3

Fresh v0.9 projects use orchestration schema 3. Existing schema-2 events remain
byte-for-byte intact and one `orchestration.migrated` event appends the 2 -> 3
boundary. Validation accepts the already-supported 1 -> 2 boundary followed by
at most one 2 -> 3 boundary and rejects downgrade, skipped versions, duplicate
boundaries, old-schema events after migration, or a final state/log mismatch.

Schema 3 adds optional project rotation policy/history and optional task budget
policy/state. Migration does not create a budget, invent a session binding,
record a usage observation, recommend rotation, or change a task state.

A task budget contains:

- at least one positive soft or hard total-token limit; when both exist,
  `soft < hard`;
- selected root session ID and canonical start event identity;
- last explicit observation summary and hash-bound canonical event identity;
- threshold status (`within`, `soft-exceeded`, or `decision-required`);
- bounded supervisor decisions with actor, reason, action, evidence, prior
  observation identity, and any explicitly added allowance.

A project rotation policy contains optional thresholds for supervisor current
context, compactions, wait calls/duration, and completed tasks. Rotation history
binds the old root session, final measurement interval/report identity,
canonical handoff event/checkpoint, explicit recommendation reasons, new root
session, and verification event.

`STATUS.md`, status JSON, handoff, check, upgrade, uninstall, and recovery
validate and preserve schema-3 records. State migration and explicit budget or
rotation mutations reuse the existing orchestration lock and pending
transaction; no report holds the mutex while reading rollouts through the App
Server.

### Local task budgets

Budgets are opt-in and measured only in raw total tokens. A task budget must be
bound to one root session and exact canonical start event before enforcement;
changing either requires an explicit policy-replacement event that preserves
history.

Budget evaluation has two surfaces:

1. A read-only report computes current usage and warnings. It never changes
   task state or makes later mutations illegal by itself.
2. An explicit observation command recomputes the same report, rechecks the
   canonical interval and rollout provenance, and appends a
   `task.budget-observed` event with the normalized summary.

Crossing a configured soft limit produces a warning. Recording an observation
at or above a configured hard limit sets `decision-required`; it does not set
`BLOCKED`, alter acceptance/verification, revoke a lease, or claim completion.
While a hard decision is required, Synod refuses a new acquisition, heartbeat,
resume/reassignment, ordinary correction, or transition that authorizes more
execution. It still allows release/revocation, proposal sealing, review,
acceptance, verification, split, supersession, status, handoff, export, and
recovery actions.

The supervisor resolves the exact observation explicitly by choosing a bounded
continuation allowance, split, supersession, or phase rotation with actor,
reason, and evidence. A stale decision for an older observation or policy
revision is rejected. Continuing increases the hard allowance; it never resets
measured usage or deletes threshold history.

### Phase-rotation recommendation and handshake

The recommendation engine combines canonical handoff state with a usage and
coordination report for the current phase interval. It evaluates only configured
thresholds and reports every triggering metric, current value, threshold,
completeness, and source interval. No threshold is enabled by default.

Supervisor context uses the latest root-thread `last_token_usage.input_tokens`
observation and its reported model context window. It is separate from
cumulative input tokens. If the active Codex version omits either value, that
threshold is unavailable and cannot trigger from a guessed value.

Rotation remains explicit:

- `prepare` captures a closed local report, validates the canonical handoff,
  and appends a recommendation event without changing tasks;
- the supervisor starts a new root session through Codex, outside Synod;
- `verify` in that new session re-reads the canonical state/event chain,
  checkpoint, unresolved gates, and prepared recommendation, rejects reuse of
  the old root, and appends the verified new-root binding;
- only the verified new phase becomes the start boundary for later completed
  task and coordination thresholds.

Preparing or verifying a rotation does not archive, rename, pin, fork, create,
or message a Codex thread; it records and verifies identities only.

### Optional cost estimates

Cost estimation is a pure projection over a completed usage report. It is
enabled only by an explicit price-file argument. The versioned local file
contains currency, `asOf`, optional validity end, source/reference text, and
exact per-million rates by model for uncached input, cached input, and output.

The estimator uses:

- uncached input = input minus cached input;
- cached input = cached input;
- output = output, already inclusive of reasoning output.

Reasoning is displayed as evidence but is not charged again. Exact model-name
matching prevents a rerouted or unknown model from inheriting another model's
price. Missing model rates make the estimate partial, list unpriced token rows,
and prevent a misleading grand total. Currency conversion, tax, tiered volume,
provider credits, subscription allocation, and live price fetching are outside
v0.9.

## Delivery sequence

Use five reviewable pull requests against protected `main`:

1. SYN-090A/B: normalized timelines, canonical interval selectors, and
   thread/model/role marginal usage.
2. SYN-091A: coordination classification, counts, durations, and completeness.
3. SYN-092A: schema-3 migration, task budget observation, decisions, and gates.
4. SYN-093A/094A: handoff rotation recommendation/handshake and optional dated
   cost projections.
5. Release closure: migration/compatibility closure, production-shaped fixtures,
   cross-platform installed smoke, docs, and `v0.9.0` release preparation.

Each pull request keeps the full suite, typecheck, package smoke, compatibility
smoke, and `git diff --check` green. No new production dependency may be added
without explicit approval. The final release follows the existing reviewed
squash-merge, Codex review, signed-tag, protected npm environment, npm/GitHub
parity, provenance, and installed CLI verification path.

## Definition of v0.9 ready to release

- Event, checkpoint, and task selectors resolve one validated canonical
  interval with explicit boundary, provenance, and completeness metadata.
- Marginal token deltas survive counter resets and model reroutes without
  double counting and remain attributable by thread, model, and role.
- Coordination counts/durations are distinct from implementation tool activity;
  unsupported retry or duration evidence is unavailable rather than invented.
- Optional task budgets warn softly and require one exact supervisor decision
  after a recorded hard crossing without forging task state or completion.
- Configured phase thresholds produce a reproducible canonical handoff
  recommendation, and an explicit new-session verification binds the next
  phase before its metrics begin.
- Optional cost output uses only dated caller-supplied prices, preserves raw
  tokens, avoids reasoning double charge, and is absent by default.
- Reporting remains local and read-only; no command uploads telemetry, fetches
  prices, changes Git, mutates a Codex thread, or spends provider funds.
- A production-shaped multi-task fixture passes the release gate through the
  installed package on every supported CI runtime, including active/incomplete
  labelling, archived descendants, reroutes, resets, compactions, and waits.
